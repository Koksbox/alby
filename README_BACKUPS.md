# Настройка Alby и резервного копирования

Вход, пароли, должности и оформление существующих страниц сохранены. В кабинете
директора добавлены только подключение Яндекс Диска и состояние копирования.
Ручной кнопки создания копии нет. Бекапы выполняет отдельный worker.

## Первый запуск

1. Установите зависимости: `python -m pip install -r requirements.txt`.
2. Скопируйте `.env.example` в `.env`, если `.env` ещё нет. Не перезаписывайте файл
   с существующими настройками. `.env` не попадает в Git и Docker image.
3. Создайте ключ для хранения OAuth-токенов:

   ```sh
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```

   Вставьте результат в `BACKUP_ENCRYPTION_KEY`. Сохраните этот ключ отдельно от БД:
   он понадобится после восстановления для чтения сохранённого подключения.
4. Укажите `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI`.
   Redirect URI должен точно совпадать с настройкой приложения Яндекса.
   Для localhost: `http://localhost:8000/director/backups/yandex/callback/`.
   На сервере используйте реальный HTTPS-домен.
5. Для папки приложения нужны права `cloud_api:disk.app_folder` и путь
   `YANDEX_BACKUP_ROOT=app:/AlbyBackups`. Для приложения с правами чтения/записи всего
   Диска можно задать `disk:/AlbyBackups` и соответствующий `YANDEX_OAUTH_SCOPE`.
6. Выполните `python manage.py migrate`, запустите приложение и войдите обычным
   способом как директор. В его кабинете нажмите «Подключить Яндекс Диск».
7. Задайте интервал, затем `BACKUP_ENABLED=1` и запустите worker:

   ```sh
   python manage.py run_backup_worker
   ```

При включённом копировании первый комплект создаётся после старта worker, если
успешных запусков ещё не было. Открытие страницы и подключение Диска сами по себе
копию не создают. По умолчанию в примере копирование выключено.

Можно вместо кнопки указать готовые `YANDEX_ACCESS_TOKEN` и `YANDEX_REFRESH_TOKEN`.
Worker перенесёт их в зашифрованное хранилище. После подключения БД имеет приоритет
над начальными токенами в `.env`; для замены используйте переподключение.

## Отключить Диск перед передачей проекта

`YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` относятся к OAuth-приложению: их можно
оставить. Access/refresh-токены относятся к конкретному Яндекс-аккаунту. Команда
ниже **только помечает подключение отключённым** и отменяет незавершённые
OAuth-подключения, сохраняя вход в сайт. `.env`, токены в БД, ключ шифрования,
реквизиты приложения, пароли, рабочие данные, архивы и история не меняются.
Worker учитывает отметку отключения: не использует сохранённый токен и не
импортирует старый токен из `.env` до успешного нового OAuth-подключения.
Команда не отзывает разрешение в аккаунте Яндекса.

После переноса обновлённого кода на сервер, из каталога проекта:

```sh
docker compose up -d --build --force-recreate
docker compose exec web python manage.py disconnect_yandex_disk
```

Первая команда нужна один раз для установки обновлённого кода и миграции.
Для следующих отвязок достаточно второй команды. Она отказывается менять
подключение во время копирования: дождитесь завершения или остановите worker
(`docker compose stop worker`), выполните отвязку и верните worker
(`docker compose start worker`). Перезапуск после самой отвязки не требуется.

Без Docker: примените миграции (`python manage.py migrate`), затем выполните
`python manage.py disconnect_yandex_disk`. После успешного подключения нового
владельца через кнопку worker продолжит расписание автоматически, если
`BACKUP_ENABLED=1`. Обычная кнопка требует доступного callback, который
принимает Яндекс; в проверенной установке HTTP-callback на IP отклонялся,
поэтому для передачи с подключением кнопкой настройте собственный HTTPS-адрес.

## Расписание и тестирование интервала

```dotenv
# Каждые 3 дня:
BACKUP_INTERVAL_DAYS=3
BACKUP_INTERVAL_HOURS=0

# Для проверки каждый час: DAYS=0, HOURS=1.
# Пример примерно раз в минуту: DAYS=0, HOURS=0.016667.
```

Дни и часы суммируются. Интервал отсчитывается от последней полностью успешной
доставки. Изменение `.env` требует перезапуска worker (в Docker — пересоздания
контейнера командой `docker compose up -d --force-recreate worker`). Новый интервал
применяется к сохранённой дате последнего успеха. После ошибки тот же комплект
повторяется через `BACKUP_RETRY_SECONDS`, а не через три дня.

`python manage.py run_backup_worker --once` проверяет расписание один раз и
**может создать настоящую копию**, если она включена и наступил срок.
Для проверки кода без настоящего копирования запускайте тесты:

```sh
python manage.py test --noinput
python manage.py makemigrations --check --dry-run
```

## Два контейнера

```sh
docker compose up --build -d
docker compose logs -f worker
```

`web` выполняет миграции и collectstatic, затем запускает Gunicorn; `worker`
ожидает готовности web. База SQLite находится в `./data/db.sqlite3`, фотографии —
в `./media`, бекапы и блокировки — в `./var`. Эти каталоги постоянные, вне
контейнеров. В worker фотографии подключены только для чтения. Не запускайте
worker с другим staging-каталогом: блокировка снимка должна быть общей с web.

Для существующей установки перед переходом на Docker остановите запись в старое
приложение и перенесите существующую SQLite в `data/db.sqlite3`; не начинайте работу
с пустой БД вместо рабочей. Для открытой SQLite используйте `sqlite3.Connection.backup`,
а не файловое копирование. При `DATABASE_URL` оба контейнера используют указанную
внешнюю БД, перенос SQLite не нужен. При нативном запуске исходный путь БД сохраняется.

Порт привязан к `127.0.0.1:8000`. При `DJANGO_DEBUG=0` существующий reverse proxy
сервера должен отдавать `/media/` из каталога `media` и передавать запросы Gunicorn.
WhiteNoise отдаёт собранную статику. PostgreSQL и reverse proxy в эти два контейнера
не входят; автоматически менять серверную БД эта доработка не будет.
Образ содержит pg_dump из Debian Bookworm; при внешней PostgreSQL новее клиента
установите в образ совместимый pg_dump и укажите `BACKUP_PG_DUMP_BINARY`.

## Что сохраняется и как удаляются старые копии

Каждый комплект имеет собственный UUID и содержит:

- `alby_db_<дата>_<id>.zip` — согласованный снимок SQLite либо дамп PostgreSQL;
- `alby_media_<дата>_<id>.zip` — вся папка `media/`, включая аватары и вложения;
- `manifest.json` — размеры, SHA-256/MD5, дата и идентификатор комплекта.

Изображения не пересжимаются и не переименовываются. Существующая логика загрузки
изображений и ограничения форматов не меняются. `static/` восстанавливается из
проекта и collectstatic; уникальные пользовательские файлы должны находиться в
`media/`. ZIP-файлы не зашифрованы; OAuth-токены в БД зашифрованы отдельным ключом.

Локальное направление — каталог `BACKUP_LOCAL_ROOT` на том же сервере, без SSH.
Его нельзя помещать внутрь `media/` или `static/`, как и staging. Это подготовка
второго направления хранения; перенос на отдельный сервер пока не реализован.
Локальная копия на том же диске не защищает от потери всего сервера.

Хранятся **два последних полностью успешных комплекта**. После подтверждения
третьего на обоих направлениях удаляется самый старый, остаются третий и второй.
При ошибке хотя бы одного направления старые успешные комплекты не ротируются.
Незавершённый новый комплект может временно присутствовать на одном направлении.
Повтор отправляет те же архивы и проверяет уже доставленные. Временные ZIP
удаляются только после успеха; рабочая БД и исходные фотографии не удаляются.
Удаление ограничено UUID-каталогом с совпадающим manifest, чужие файлы не трогаются.
Сбои очистки повторяются отдельно от создания следующего комплекта.

На время снимка/упаковки `media/` загрузки и удаления файлов ожидают общую
блокировку. Просмотр и обычные операции с задачами/сменами продолжают работать.
Во время сетевой отправки блокировка уже снята. Переименование/удаление файлов
напрямую в ОС в обход приложения может прервать снимок; комплект не будет признан
успешным. Staging — постоянный каталог, его нельзя чистить во время незавершённого
запуска. При повреждении staging и отсутствии проверенного локального экземпляра
worker сохраняет ошибку вместо подмены согласованного снимка другим содержимым.

## Восстановление

1. Выберите **один UUID-комплект**, проверьте SHA-256 обоих ZIP по manifest.
2. Остановите web/worker и восстановите сначала в отдельный тестовый каталог/БД.
3. Для SQLite извлеките `database.sqlite3`; для PostgreSQL извлеките
   `database.dump` и используйте совместимый `pg_restore` в пустую тестовую БД.
4. Распакуйте второй архив с сохранением путей `media/...`.
5. Подключите ту же версию проекта/миграций, выполните проверку SQLite
   `PRAGMA quick_check` либо проверьте восстановленный PostgreSQL.
6. Проверьте вход, задачи, фото, смены и начисления. Затем переключайте рабочую
   установку. Первую загрузку после восстановления выполняйте с `BACKUP_ENABLED=0`.

Восстановленная БД содержит историю worker на момент снимка. После ручного выбора
старого комплекта проверьте состояние `BackupRun`/`BackupSchedule` до повторного
включения worker. Ни восстановление поверх рабочей БД, ни реальный запуск бекапа
не выполняются автоматически при открытии страниц.

## Изменения смен и периодов

Все старые и новые обработчики старта используют один сервис. БД запрещает вторую
открытую смену сотрудника/менеджера. Повторный старт возвращает существующую смену.
При миграции существующие дубли открытых таймеров приводятся к непересекающимся
интервалам; закрытая история не пересчитывается. Сохраняются исходные записи и ставки.

Период на всех экранах: начало включительно, следующая календарная граница
исключительно, в часовом поясе Asia/Yekaterinburg. Вся смена относится к периоду
начала. Ночная смена 31 января → 1 февраля целиком учитывается в январе.
Ставка берётся из записи смены; для старых записей без неё остаётся текущая ставка.

Явное право `backups.manage_backups` выдаётся существующему директору миграцией.
Автоматически созданный прежним механизмом входа аккаунт директора также получает
это право. Идентификация директора по email и существующие роли не изменены.
Менеджеры не получают доступ к подключению или состоянию бекапов.
